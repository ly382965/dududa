# Dududa 3.0 本地运行

以下步骤面向 Linux / WSL，启动独立的 3.0 Host，并让 Web / QQ 适配器调用它。旧 `manage.sh`、AstrBot 主执行链和 Docker Compose 已收进 `legacy/2.0/`，不用于本步骤。

## 准备与规则验证

在仓库根目录执行：

```bash
uv sync --locked --python 3.12
codex --version
codex login status
uv run --locked dududa-v3 --config configs/runtime-v3.example.json check
uv run --locked dududa-v3 chat '/ping'
uv run --locked dududa-v3 chat '/校车 工作日东区到西区'
```

`check` 只检查本机可执行文件，不代表模型调用已经成功。规则通过同一个 3.0 Runtime 执行，返回结果中的 `route` 为 `rule`；这些命令不调用模型。首次 Agent 验证可执行：

```bash
uv run --locked dududa-v3 chat '你好，请简短介绍自己。' --conversation private:demo
uv run --locked dududa-v3 chat '请接着上一句继续。' --conversation private:demo
```

两次使用相同会话会复用 Codex thread。同一状态目录只允许一个 `chat` / `serve` 进程，重复启动会明确报错。需要独立测试状态时，设置 `DUDUDA_V3_STATE_DIR` 指向另一个目录。

## 启动 HTTP Host

```bash
uv run --locked dududa-v3 --config configs/runtime-v3.example.json serve
```

默认监听 `127.0.0.1:8783`。`--config` 必须放在子命令之前。省略时使用默认配置，不自动加载示例文件。修改端口可使用 `serve --port 8784`。

未设置 `DUDUDA_V3_TOKEN` 时，Host 首次生成权限为 `0600` 的 `runtime/v3/token`，之后复用该文件；终端只显示路径，不输出 token。如果设置了该环境变量，Host 使用指定值，Web 也要使用相同值。

默认运行数据：

| 路径 | 内容 |
| --- | --- |
| `runtime/v3/token` | HTTP 访问令牌 |
| `runtime/v3/runtime.sqlite3` | 会话、任务、消息、显式记忆和投递记录 |
| `runtime/v3/workspaces/` | 按会话隔离的 Codex 工作目录 |
| `runtime/v3/host.lock` | 同一状态目录的进程互斥锁 |

Codex 自己的登录、配置与 thread 数据仍由本机 Codex 管理；上述目录不是其完整备份。

本机验收使用的 CLI 在恢复旧 thread 时会保留初始开发指令。Host 因而保存一个执行配置版本；版本变化时新建执行 thread，原群聊记录、显式记忆和旧运行记录不删除，版本一致时继续恢复同一 thread。更新开发指令或工具输出规则时，需要同步 `SESSION_PROFILE`。

## 启动 Web

另开终端，在仓库根目录执行：

```bash
export DUDUDA_RUNTIME_VERSION=3
export DUDUDA_V3_URL=http://127.0.0.1:8783
export DUDUDA_V3_TOKEN_FILE="$PWD/runtime/v3/token"
cd apps/web
npm ci
npm run dev
```

打开 <http://127.0.0.1:5173>，在 Agent 预览输入 `/ping`，然后测试自然语言请求。预览应标明 3.0；规则请求不显示为模型生成。Web 默认选择 3.0，Host 不可达或返回错误版本时直接报错，不回退到 2.0。

`DUDUDA_V3_TOKEN` 在 Web 中优先于 token 文件。若使用文件模式，确保启动终端没有遗留的旧 token 环境变量。从 `apps/web` 启动时，Web 默认查找 `../../runtime/v3/token`。上述显式设置也适用于使用自定义状态目录的情况，只需改成实际令牌文件路径。

## 开放一个 QQ 测试会话

在 Web 工作区连接 LLOneBot / NapCat，取得实际 `accountId` 与 `conversationId`。范围格式为 `accountId/conversationId`；多个范围以英文逗号分隔。以下仅为 ID 格式示例：

```bash
export DUDUDA_V3_QQ_SCOPES='qq-100001/qq-100001:group:200001'
```

Host 和 Web 两个启动终端都需要设置相同白名单，再分别重启。也可将 Host 的范围写入 JSON 的 `allowed_scopes`；环境变量存在时会覆盖该字段。默认空范围不会自动处理和发送 QQ 回复。

规则命令直接匹配；普通群消息默认需要 @ 机器人。配置 `proactive_scopes` 可允许指定范围主动参与，并由 `proactive_cooldown_seconds` 控制间隔，默认冷却 120 秒。此配置与旧 Web 群策略页面相互独立。

同一群的旧 AstrBot 回复插件与 3.0 不应同时处理同一触发消息。QQ 发送由适配器负责，并通过 Host 的投递记录避免相同任务重复发送；结果未知时不会自动重发。Web 预览始终不发送 QQ 消息。

## 配置字段

复制 [配置示例](../../configs/runtime-v3.example.json) 后按需修改，再通过 `--config` 加载。

| 字段 | 默认值与说明 |
| --- | --- |
| `state_dir` | `runtime/v3`；相对路径以仓库根目录为基准 |
| `codex_binary` | `codex`；也可指定本机 CLI 的绝对路径 |
| `model` | `gpt-5.6-luna`；每次新建、恢复与执行均显式指定 |
| `reasoning_effort` | `max`；每一轮请求显式传入，Web 与运行记录显示实际值 |
| `timeout_seconds` | `180`；单次 Agent 执行超时 |
| `concurrency` | `2`；跨会话并发数，允许 1–8 |
| `allowed_scopes` | 空数组；允许 QQ / timer 进入的会话范围 |
| `proactive_scopes` | 空数组；允许非 @ 群消息进入 Agent 的范围 |
| `proactive_cooldown_seconds` | `120`；主动参与冷却秒数 |
| `proactive_policies` | 按 `accountId/conversationId` 保存旧会话的概率、冷却、每小时上限和最少上下文条数 |
| `rules` | 精确文本匹配数组，每项包含 `match`、`reply` |
| `mcp_console_url` | `null`；共享 MCP Console 的 HTTP 地址 |
| `qq_gateway_url` | `null`；当前 Web/OneBot 网关地址。配置后每轮 QQ 智能请求自动读取最近 3 小时内最多 30 条；总结时模型使用 `conversation_history` 按时间分页读取，最多 1000 条 |
| `campus_capabilities` | 空数组；显式开放的公开校园能力 ID |

Host 另支持 `DUDUDA_REPOSITORY`、`DUDUDA_V3_STATE_DIR`、`DUDUDA_V3_CODEX_BINARY`、`DUDUDA_V3_MODEL`、`DUDUDA_V3_REASONING_EFFORT` 和 `DUDUDA_V3_QQ_SCOPES` 覆盖对应配置。`DUDUDA_REPOSITORY` 用于从其他目录启动时定位仓库。

与旧规则插件并行运行时，停用旧 `astrbot_plugin_dududa_core` 智能回复和与新 Host 重复的内置命令插件，保留其他独立规则插件。3.0 不认领的 QQ 斜杠命令不会调用 Codex，继续由对应规则插件处理。构建新版 Web 镜像可使用 `deploy/v3/Dockerfile.web`；本机 Codex Host 应在宿主机以登录用户运行，容器仅通过带令牌的内部 HTTP 接口访问它。

根 workspace 不安装旧 `dududa-agent` 或启动全部校园 MCP。使用 Console 时，需独立准备其原有依赖与部署环境，配置可访问的地址及公开能力白名单。当前私有 CAS 数据和外部提交能力不开放给 3.0 MCP；默认仅提供本地校车、会话上下文和记忆查询。

## 调用 HTTP API

所有请求都需要 token。下面用本地 Python 读取文件并调用接口，不向终端打印 token：

```bash
uv run --locked python - <<'PY'
import json
from pathlib import Path
from urllib.request import Request, urlopen

token = Path('runtime/v3/token').read_text().strip()
request = Request('http://127.0.0.1:8783/v3/health',
                  headers={'Authorization': 'Bearer ' + token})
with urlopen(request) as response:
    print(json.dumps(json.load(response), ensure_ascii=False, indent=2))
PY
```

创建任务、查询状态、取消和投递接口见 [Runtime 设计](../design/dududa-3.0-runtime.md#http-api)。对运行中的服务使用 `/v3/health` 查看活动任务；CLI `check` 仅查看可执行文件，不修改运行状态。

## 验证与排查

```bash
uv run --locked python -m unittest discover -s tests/v3 -v
uv run --locked python ops/cli/verify_dududa_v3.py --output runtime/v3/verification.json
```

第二条命令必须经过新 Runtime 调用真实本机 CLI，没有 stub 开关。它需要可用认证和模型网络，并会产生真实调用。协议单元测试可用明确标识的测试进程，但不能代替这项验证。

常见问题：

| 现象 | 检查 |
| --- | --- |
| `This state directory is in use` | 当前目录已有 `serve` 或 `chat`；使用运行中 Host，或另设 `DUDUDA_V3_STATE_DIR` |
| `codex_available: false` | 运行进程的 PATH 或 `codex_binary` 配置 |
| 本机 CLI 存在但 Agent 失败 | 同一用户下的 Codex 登录、模型配置和网络；查看 run 的 `error` |
| Web 认证失败 | token 环境变量是否覆盖了正确文件，Host 与 Web 是否一致 |
| QQ 请求 403 或没有被处理 | 两端白名单是否一致，账号及会话 ID 是否准确 |
| 校园能力不可用 | Console 是否独立运行，能力是否公开、可用并列入白名单 |
| 旧 UI 改模型或人格后无变化 | 旧配置未控制新 Host；模型在本机 Codex，默认人格在 `configs/personas/dududa.md` |

本次测试证据见 [2026-10-15 验证记录](v3-validation-2026-10-15.md)。历史 2.0 基准和录制结果不用于宣称 3.0 通过。
