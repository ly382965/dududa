# Dududa 3.1 运维手册

本文描述线上 3.1.0 的部署布局、发布与回滚、配置和排障。本地开发启动见 [README 快速开始](../../README.md#快速开始)，代码边界与 HTTP 接口见 [Runtime 设计](../design/dududa-3.0-runtime.md)。

## 运行组成

| 组件 | 形态 | 说明 |
| --- | --- | --- |
| Dududa Host | systemd 用户服务 `dududa-v3.service` | Python 进程，监听 `172.23.0.1:8783`（Docker 网桥地址，供 Web 容器访问） |
| omp | `/home/mmdustc/.local/bin/omp`（18.12.1） | Host 每次 Agent 运行启动一个 `omp --mode rpc` 子进程；登录和模型凭据由 omp 管理 |
| Dududa Web | 容器 `dududa-web-1`，镜像 `dududa/web:3.1.0` | Web 控制台与 QQ 桥；对宿主发布 `127.0.0.1:5173` |
| NapCat | 容器 `mmdustc-bot-astrbot-qq-napcat-1` | QQ 协议端，只连接 `ws://dududa-web-api:8000/onebot/v11/ws`；WebUI 在宿主 `[::1]:6099` |
| MCP Console | 容器 `dududa-mcp-console-1` | 校园能力服务，宿主 `127.0.0.1:8090` |

AstrBot 已完全移除（`dududa-astrbot-1`、`dududa-llbot-1`、`dududa-recording-astrbot` 均已删除）。NapCat 容器名和数据目录沿用历史名称，与 AstrBot 无关。

消息链路：NapCat → Web（OneBot v11 WebSocket）→ Host `POST /v3/runs` → Web 轮询 run 结果并按动作发送 → Web 回报 `/v3/runs/{id}/delivery`。主动消息走 [outbox](#outbox)。

## 发布

以版本 `<ver>`、提交 `<commit>` 为例，在仓库根目录和 `dududa-state` 之间操作：

```bash
cd /home/mmdustc/Code/dududa
.venv/bin/python -m unittest discover -s tests/v3
(cd apps/web && npm test && npm run build)
git commit ...                                   # 记下 <commit>

state=/home/mmdustc/Code/dududa-state
mkdir -p $state/releases/<ver>/source
git archive <commit> | tar -x -C $state/releases/<ver>/source

cd $state/releases/<ver>
uv venv --python 3.12 source/.venv
uv pip install --python source/.venv/bin/python ./source/packages/dududa-runtime
cp ../<上一版本>/runtime.json ../<上一版本>/host.env ../<上一版本>/web.compose.json .
# 如有新配置字段，在此修改 runtime.json；Web 镜像变更时更新 web.compose.json 的 image
source/.venv/bin/python -m dududa_v3 --config runtime.json check

cd $state
ln -sfn releases/<ver> current
systemctl --user restart dududa-v3
```

Web 镜像在仓库根目录构建，再从 `dududa-state` 启动：

```bash

docker compose -p dududa -f current/web.compose.json up -d web
```

发布后检查：`journalctl --user -u dududa-v3 -n 20` 出现 `listening at http://172.23.0.1:8783`；在测试会话发送 `嘟嘟哒 status`，确认版本与模型；需要时运行真实链路验证：

```bash

.venv/bin/python ops/cli/verify_dududa_v3.py --config ../runtime.json --output /tmp/dududa-verify.json
```

## Outbox

主动消息（定时推送、通知、告警）不直接调用 QQ，而是写入 Host 的 outbox：

| 来源 | 方式 |
| --- | --- |
| 功能模块 | `ctx.push("accountId/conversationId", reply, dedupe=...)` |
| 外部本机进程 | `POST /v3/outbox`，Bearer token 认证 |

```json
{
  "account_id": "qq-<机器人QQ号>",
  "conversation_id": "qq-<机器人QQ号>:private:<收件人QQ号>",
  "actions": [{"type": "text", "text": "提醒内容"}],
  "dedupe": "my-job:2026-10-19"
}
```

`account_id/conversation_id` 必须在 `allowed_scopes` 中，否则返回 403；请求体上限 16 MiB；相同 `dedupe` 只入队一次。动作类型：

| 类型 | 字段 |
| --- | --- |
| `text` | `text` |
| `image` | `data`（base64）+ `mime`，或 `url` |
| `face` | `id`（QQ 表情 ID） |
| `forward` | `nodes`：每个节点 `{name, actions}`，合并转发 |
| `reaction` | `message_id`、`emoji_id` |
| `file` | `name`、`data`（base64） |

QQ 桥每 3 秒调用 `POST /v3/outbox/claim`（条目从 `pending` 变为 `sending`），按顺序发送后回报 `POST /v3/outbox/{id}/result`，`state` 为 `sent` 或 `unknown`。发送结果不确定的条目记为 `unknown`，不会自动重试，以免重复刷屏；需要重发时手动重新入队。

`features/notify` 移植自 AstrBot 插件 `astrbot_plugin_dududa_notify`，保留原 SQLite 布局，状态位于 `v3/features/notify/`。

**worker 环境**：校园访问、PDF / PNG 渲染和课程资料读取在独立虚拟环境中运行，Host 不导入这些模块。

```bash

```

`features.notify.worker_python` 为空时默认使用上述路径。worker-venv 不随发布目录变化，重装依赖时才需重建。

**状态迁移**：3.1.0 上线时已用 `ops/cli/migrate_notify_state.sh <state_dir>/features/notify` 从停止的 AstrBot 容器复制去重记录、作业 / 课程 / 周汇报数据库、字体和门户诊断数据；目标目录非空时脚本拒绝覆盖。AstrBot 容器已删除，脚本仅在重新从备份容器迁移时使用（`DUDUDA_ASTRBOT_CONTAINER` 指定容器名）。

**任务与开关**：`notify_seminar`、`notify_homework`、`notify_courses`、`notify_weekly`、`notify_auto_submit`，可用 `task on|off|reset` 管理。`notify_auto_submit` 未手动设置时跟随 `homework_auto_submit_enabled`；`dry_run: true` 阻止全部自动写操作。主人私聊指令为 `作业 …`、`课程 …`、`周汇报 状态`。

## Sub2API 用量统计（sub2api）

`features/sub2api` 移植自 AstrBot 插件 `astrbot_plugin_sub2api_readonly`（3.1.0 线上部署版与 `legacy/2.0` 源码一致）。客户端只允许固定的只读 GET 路径和登录 POST，令牌只保存在内存，不跟随重定向；`base_url` 与费用分摊快照 `https://mmdustc.top/api/projects/cost/overview` 按 `direct_hosts` / `proxy_url` 策略访问。原插件依赖的 Web 控制面策略文件（`DUDUDA_AGENT_POLICY_PATH`）在 3.1 中由任务开关 `sub2api` 与白名单取代。

**独占群**：`exclusive_groups` 通过 `Gate` 在路由前生效，被拦下的 run 记为 `ignored`、`reason` 为 `gate:sub2api`。

**趋势图**：`charts.py` 以 `chart_python -I charts.py` 独立运行（stdin JSON、stdout PNG），默认复用 notify 的 worker-venv（已含 Pillow）；字体取 `/usr/share/fonts/truetype/dejavu/`。

## 亲密度（affinity，隐藏机制）

`features/affinity` 按 QQ 号给每个人记 −100~100 的分数（跨群共享），只影响嘟嘟哒的语气，不出现在帮助菜单里。超级管理员（`features.affinity.super_admin`）固定 120。任务开关 `affinity`，关闭后不再注入关系提示和计分规则，但仍会清除模型输出中的标记。

- **计分**：聊天 Agent 的每次回复末尾带隐藏标记 `[[aff:<分值>:<类型>]]`，宿主删除标记后按类型限幅入账：chat 0~1、thanks 1~2、praise 2~5、rude −2~−5、insult −6~−12、abuse −15~−20、beg/none 0。只对叫到嘟嘟哒的消息计分；宿主事件另计：当天第一次互动 +1，触发频率限制或 ping 防刷 −1。
- **节流**：−60~60 之间不打折、无每日上限；继续往 ±100 方向变化时乘以 (100−|分数|)/40，并有每日上限 +4 / −15。加分有 2 分钟冷却，同一句夸奖 24 小时只记一次。
- **回归**：每小时检查一次。分数高于 30 且 14 天没有互动，每周 −1，最低到 30；分数低于 0 且 3 天没有新的冒犯，每 3 天 +1，最高到 0。
- **档位**：讨厌 ≤−51、不反感 −50~−11、普通 −10~30、喜欢 31~60、非常喜欢 ≥61。
- **讨厌档**：语气明显很差（冷淡、不耐烦、带刺，但不说脏话、不人身攻击）。叫她提问时按概率拒答：−51 分时 30%，线性升到 −100 分时 80%（`features.affinity.refuse_min` / `refuse_max`）；由宿主掷骰，命中时要求模型只用一句冷淡的话拒绝，涉及人身安全或紧急求助时仍认真回应。主动插话不会拒答。
- **指令**：`亲密度`（`/亲密度`、`嘟嘟哒 亲密度`、`/亲密度排行`；手打的 `@嘟嘟哒 /亲密度` 也算）。亲密度 > 60 的人：群里显示本群排行图（置顶超级管理员，最近 90 天在本群叫过她的人 Top 5 + Low 5，不超过 10 人时合成一张），私聊显示其最近活跃的群的排行；排行不显示查询者自己的分数。超级管理员：群里显示本群排行，私聊显示所有人的亲密度（含 QQ 号，按分数排序）。其他人在群里发 `/亲密度` 会像未知指令一样被忽略，用其他方式叫她则按普通聊天处理。管理员子命令：`亲密度 查 <QQ>`、`亲密度 设 <QQ> <值>`、`亲密度 记录 <QQ>`。
- **数据**：`runtime.sqlite3` 中的 `affinity`（当前分数）、`affinity_events`（全部流水，用于审计和回滚）、`affinity_seen`（谁在哪个群出现过、群名片）三张表；头像缓存在 `v3/features/affinity/avatars/`。
- **初始值**：2026-10-19 用最近约 90 天的 QQ 历史（经 Web 网关读取，共 24.8 万条消息，其中 925 条叫到或提到嘟嘟哒）按同一套规则回放算出，每条由 GPT-5.6 Luna（low）判定类型。70 人得到初值（−3.5~26.8，全部落在“普通”），以 `seed:history` 事件写入流水；逐人明细在 `v3/features/affinity/seed-2026-10-19.json`，写入前的数据库备份在 `v3/backups/`。
- **配置**：`features.affinity` 支持 `super_admin`（固定 120、私聊可看全部亲密度的 QQ，未设置则没有超级管理员）、`exclude`（不计分的 QQ，如其他机器人，默认空）、`render_python`（默认 notify 的 worker venv）、`font` / `font_bold`（默认 Noto Sans CJK）。

## 排障

| 现象 | 检查 |
| --- | --- |
| 机器人完全不回复 | `systemctl --user status dududa-v3`；`journalctl --user -u dududa-v3 -n 100`；`docker logs --tail 100 dududa-web-1` 中 Host 请求是否报错 |
| Web 日志显示 OneBot 未连接 | NapCat 是否在运行（`docker ps`），WebUI 网络配置是否指向 `ws://dududa-web-api:8000/onebot/v11/ws` 且 token 与 `secrets/web/onebot_access_token` 一致 |
| 改了 NapCat 网络配置不生效 | 在 WebUI（宿主 `http://[::1]:6099`，远程用 SSH 端口转发）中保存后需点击应用 / 启用该连接，或重启 NapCat 容器；配置文件位于 `/home/mmdustc/Code/mmdustc.top/deploy/stacks/bot-astrbot-qq/data/napcat/config/` |
| 指令有回应但提问失败 | run 的 `error`；`omp --version` 和 omp 登录状态；`journalctl` 中 `OmpError` / `OmpTimeout` |
| `This state directory is in use` | 已有 Host 占用该 `state_dir`；使用运行中 Host 的 API，或另设 `DUDUDA_V3_STATE_DIR` |
| `omp_available: false` | 单元的 `PATH` 或 `omp_binary` 配置 |
| 群里某些消息被忽略 | 是否在 `allowed_scopes`；是否点名（@ 或 `嘟嘟哒` 前缀）；未知 `/xxx` 指令会被忽略；对应任务是否被关闭（`task list`）；是否触发频率限制（run `reason=rate_limited`） |
| 主动推送没有发出 | outbox 条目状态：`pending` 表示 QQ 桥未在轮询（看 Web 日志），`unknown` 表示发送结果不确定且不会重试 |
| 校园查询不可用 | `docker ps` 中 `dududa-mcp-console-1` 是否运行，`curl http://127.0.0.1:8090`，能力是否列入 `campus_capabilities` |
| 课程资料显示无法读取 | 宿主未安装 `catdoc` / `libreoffice`，旧版 `.ppt` / `.doc` 课件会被标记为不可读 |
| 小红书归档失败 | 笔记需要登录时配置 `features.xiaohongshu.cookie` |
| 通知未推送 | `features.notify.enabled`、对应 `*_enabled`、任务开关；worker-venv 是否存在；`journalctl` 中 `notify` 相关警告 |
