# Dududa 3.1 运维手册

本文描述 3.1.16 的部署布局、SnowLuma 接入、发布与回滚、配置和排障。本地开发启动见 [README 快速开始](../../README.md#快速开始)，代码边界与 HTTP 接口见 [Runtime 设计](../design/dududa-3.0-runtime.md)。

## 运行组成

| 组件 | 形态 | 说明 |
| --- | --- | --- |
| Dududa Host | systemd 用户服务 `dududa-v3.service` | Python 进程，监听 `172.23.0.1:8783`（Docker 网桥地址，供 Web 容器访问） |
| omp | `/home/mmdustc/.local/bin/omp`（18.12.3） | Host 每次 Agent 运行启动一个 `omp --mode rpc` 子进程；登录和模型凭据由 omp 管理 |
| Dududa Web | 容器 `dududa-web-1`，镜像 `dududa/web:3.1.15` | Web 控制台与 QQ 桥；对宿主发布 `127.0.0.1:5173` |
| SnowLuma | 容器 `dududa-snowluma-1`，固定 v2.0.3 镜像摘要 | 唯一 QQ 协议端，反向连接 `ws://dududa-web-api:8000/onebot/v11/ws`；管理端 `127.0.0.1:5099`，扫码桌面 `127.0.0.1:6081` |
| MCP Console | 容器 `dududa-mcp-console-1` | 校园能力服务，宿主 `127.0.0.1:8090` |

QQ 协议端只运行 SnowLuma。NapCat 容器、镜像、旧启动配置和公网管理路由已移除；LLBot 等旧协议容器也不保留。MCP Console 继续提供校园能力，不是 QQ 协议端。旧 QQ 登录数据和账号配置仍保留在历史目录，不再挂载给运行中的协议端。

消息链路：SnowLuma → Web（OneBot v11 WebSocket）→ Host `POST /v3/runs` → Web 轮询 run 结果并按动作发送 → Web 回报 `/v3/runs/{id}/delivery`。主动消息走 [outbox](#outbox)。

QQ 的 `/help`、`/帮助`、`/菜单` 使用内置 PNG 海报；Web/CLI 仍返回按权限过滤的文字帮助。修改 `docs/assets/dududa-guide.html` 后，应使用浏览器重新渲染 `packages/dududa-runtime/src/dududa_v3/assets/dududa-guide.png`，再构建 Runtime wheel；部署不需要安装浏览器。只更新文档目录不会替换已安装的海报。

### 接入额外 QQ 账号

网关和 Host 按 `accountId/conversationId` 区分账号。新增账号应追加配置，
不能把旧账号 ID 全局替换成新账号 ID，也不要改写旧账号的会话数据库。

1. 为新账号配置 `data/gateway/config/onebot_<新QQ号>.json`，连接现有 Web 网关并使用现有 OneBot token。
   确认反向 WS 实际连通，不能只验证 QQ 登录成功。
2. 在 `runtime.json` 的 `allowed_scopes` 和 Web 的 `DUDUDA_V3_QQ_SCOPES` 中同时追加新账号范围，
   保留旧账号条目；只复制原有允许的群和私聊对象，不扩大授权。需要主动插话时，
   同步追加 `proactive_scopes` 和 `proactive_policies`。
3. 重启 Host 并重建 Web 容器以应用环境变量；仅改白名单不需要重启 SnowLuma。
   定时通知的 `features.notify.account_id` 是独立发送绑定，不随新增账号自动迁移。
4. 验收应用层账号在线、真实消息处理结果及 QQ 发送回执；TCP 已连接不代表消息通过白名单。
   补处理历史消息的验证应明确标注，不能当作新消息自动回复的验收。

SnowLuma 多账号通过各自独立的 QQ `HOME` 隔离，使用 `SNOWLUMA_EXTRA_QQ_HOMES`
和额外持久卷启动；每个账号拥有独立的 OneBot 配置。当前主账号为 `3882902131`，
旧号 `3296147894` 的白名单、策略、会话和历史均保留。旧号恢复后应分配独立 HOME，
不要覆盖新号的数据，也不要让同一账号同时运行两个客户端。

通知账号不可用时，在保留旧号权限的前提下，将 `features.notify.account_id` 指向在线账号，
确认该账号到原收件人的私聊范围同时位于 Host 和 Web 白名单，再重启 Host。
通知服务的这一个发送绑定同时用于作业、课程、讲座和周汇报；不移动或清空
`features/notify/` 下的作业、课程、提交与去重数据库，避免重发历史通知或重复提交。
验收先使用 worker 的只读 `list` / `courses` 操作查询学校，再通过同一 outbox 发送
明确标注的私聊自检消息并核对 `sent` 与 QQ 消息 ID。不能只凭调度任务 `ok` 判断投递成功，

## Outbox

主动消息（定时推送、通知、告警）不直接调用 QQ，而是写入 Host 的 outbox：

| 来源 | 方式 |
| --- | --- |
| 功能模块 | `ctx.push("accountId/conversationId", reply, dedupe=...)` |
| 外部本机进程 | `POST /v3/outbox`，Bearer token 认证 |

```json
{
  "account_id": "qq-<机器人QQ号>",
  "conversation_id": "qq-<机器人QQ号>:private:<收件人QQ号>",
  "actions": [{"type": "text", "text": "提醒内容"}],
  "dedupe": "my-job:2026-10-19"
}
```

`account_id/conversation_id` 必须在 `allowed_scopes` 中，否则返回 403；请求体上限 16 MiB；相同 `dedupe` 只入队一次。动作类型：

| 类型 | 字段 |
| --- | --- |
| `text` | `text` |
| `image` | `data`（base64）+ `mime`，或 `url` |
| `face` | `id`（QQ 表情 ID） |
| `forward` | `nodes`：每个节点 `{name, actions}`，合并转发 |
| `reaction` | `message_id`、`emoji_id` |
| `file` | `name`、`data`（base64） |

QQ 桥每 3 秒调用 `POST /v3/outbox/claim`（条目从 `pending` 变为 `sending`），按顺序发送后回报 `POST /v3/outbox/{id}/result`，`state` 为 `sent` 或 `unknown`。发送结果不确定的条目记为 `unknown`，不会自动重试，以免重复刷屏；需要重发时手动重新入队。

亲密度问候带 `guard`，领取时进入 `claimed` 而非 `sending`。Web 通过 OneBot 重新查询群成员（本人及 bot）或私聊好友，再调用 `POST /v3/outbox/{id}/authorize`，携带 `target_valid`。Host 在事务内复查开关、分数、关系、订阅版本、白名单、过期时间和当日去重后，返回最终动作并置为 `sending`。取消、降分、换目标可撤销 `pending/claimed`；授权后已派发，结果不确定仍为 `unknown`，不自动重试。普通作业、课程等通知不受此 guard 影响。

**任务与开关**：`notify_seminar`、`notify_homework`、`notify_courses`、`notify_blackboard`、`notify_weekly`、`notify_auto_submit`，可用 `task on|off|reset` 管理。`notify_blackboard` 与主人原有 `notify_courses` 独立调度；关闭前者不停止后者。`notify_auto_submit` 未手动设置时跟随 `homework_auto_submit_enabled`；`dry_run: true` 阻止全部自动写操作。主人私聊指令为 `作业 …`、`课程 …`、`周汇报 状态`。

### 独立 BB 课程订阅

在 `features.notify.blackboard_accounts` 追加账号，不替换主人原有的 `credentials_file`、`course_sources` 或课程数据库：

```json
{
  "blackboard_accounts": [
    {
      "id": "PB_ACCOUNT",
      "recipient": "300001",
      "credentials_file": "/absolute/private/notify/PB_ACCOUNT.toml",
      "term": "2026FA",
      "interval_minutes": 10,
      "summary_hour": 20
    }
  ]
}
```

`id` 必须与凭据中的统一身份认证用户名完全一致，不能填任意昵称。收件人必须同时位于 `notify.recipients` 和该机器人账号的私聊 `allowed_scopes`；新增 QQ 收件人时也应同步 Web 白名单。`enabled: false` 可停用单个订阅。省略间隔/日报时刻时继承 `courses_interval_minutes` / `courses_summary_hour`；日报使用北京时间。换学期后更新 `term`，每轮重新发现该学期课程，空课程也继续检查，但不在正常报告中占位。

凭据仅在账号持有人明确授权后保存，父目录设为 `0700`、文件设为 `0600`，不得提交仓库或粘贴日志：

```toml
username = "PB_ACCOUNT"
password = "<由账号持有人在本机填写>"
```

显式凭据文件优先于进程环境中的旧账号凭据，登录前检查用户名。使用 pyustc 完成正常统一身份认证后，BB 课程读取只允许 GET/HEAD、课程内导航及资源；拒绝答题、提交入口和跨课程重定向。该订阅没有自动提交能力，也不受主人自动提交开关授权。

课件文本通过现有 `Notify.generate → Runtime.agent_once → OmpClient` 的 `qa` 模型通道处理，默认 Luna；不另建 API 客户端，不开放模型工具，不把密码、Cookie 或登录页面送入提示。完整正文分段分析，作业必须有原文证据；只有日期时不补造 `23:59`，“下午下课前”等要求原样保留。无法提取正文的资源会标明限制。模型输出未通过校验时保留已有任务、显示分析失败并在后续轮询重试，不把失败当作无作业。

每个订阅的状态目录为 `v3/features/notify/courses-<QQ号>-<学号>/`，主人原库 `courses-<QQ号>/` 不变。课件修订缓存控制模型调用和重复提醒；首次完整报告包含历史课件，但不把全部历史任务逐条推送。之后新任务提醒、DDL 提醒和每日图文报告沿用课程通知格式。

私聊 `课程 <学号> 列表|今日|状态` 查询；`课程 完成|恢复 <学号>:C1` 或 `课程 截止 <学号>:C1 YYYY-MM-DD HH:MM` 修改本地状态。只有绑定收件人可操作，不能在群内读取。主人省略学号时仍选原课程账号；其他收件人只有一个订阅时可以省略学号。

## 亲密度（affinity，隐藏机制）

完整行为与命令以[亲密度与闺蜜规则](../design/affinity.md)为准。3.1.15 使用七档、原始分数判断，删除旧概率拒答；`/亲密度` 门槛为 ≥50，闺蜜建立为 >50，群聊优先真实 @ 本人。

- **开关**：`task off affinity` 关闭评分、态度和关系问候，并永久停订现有问候；重新开启不会自动恢复推送。退出、退订、删除本人数据及申诉仍可用。
- **计分**：保留原算法、每日奖励、去重、边缘衰减与自然回归；迁移不重算分数。用户管理请求按每日奖励之前的快照判断，确认关系和发送问候还会复查当前分数。
- **数据**：保留 `affinity`、`affinity_events`、`affinity_seen`；新增 `affinity_relationships`、`affinity_relationship_pending`、`affinity_profiles`、`affinity_preferences`、`affinity_appeals`、`affinity_social_audit`，以及 `affinity_greetings`、`affinity_greeting_pending`、`affinity_greeting_groups`、`affinity_greeting_events`、`affinity_greeting_deliveries`。头像缓存仍在 `v3/features/affinity/avatars/`。
- **隐私**：关系按用户 QQ 跨账号共享；个人称呼、偏好和约定按可信账号/会话隔离。不同群的排行不混用，私聊资料不自动带入群聊。新增关系和问候必须本人明确同意。
- **群问候授权**：当前群必须同时在 Host 的 `allowed_scopes`、`proactive_scopes` 与 Web 的 `DUDUDA_V3_QQ_SCOPES`。`/问候 群开启` 只解除群内抑制，不扩大配置白名单。私聊必须为本人且在白名单。没有自动创建任何订阅。
- **配置**：沿用 `features.affinity.super_admin`（特殊固定120）、`exclude`（排除机器人）、`render_python`（默认 notify worker venv）、`font` / `font_bold`。旧 `refuse_min/refuse_max` 已无效，应从配置移除。
- **换号与回滚**：保留旧 `affinity_seen` 和原流水；同一 QQ 群的排行跨账号继承。问候按用户/种类/日期全局去重，不因换号重复发送；跨会话换目标需确认。
- **验收证据**：252 项 Python 测试、99 项相关 Web 测试；隔离 Host HTTP → OneBot WebSocket 验收覆盖门槛、群内确认关系、实际定时 @ 问候、取消和解除。实际 PNG 渲染验证七档图例。生产库副本迁移保持 83 人分数及 339 条评分流水不变，未创建关系或订阅；未向真实 QQ 会话发送测试消息。
- **备份**：上线前 SQLite 在线备份位于 `v3/backups/before-affinity-3.1.15-20261020-232450.sqlite3`；旧发布目录与镜像保留。数据库含私人聊天，禁止提交到仓库。

## 排障

| 现象 | 检查 |
| --- | --- |
| 机器人完全不回复 | `systemctl --user status dududa-v3`；`journalctl --user -u dududa-v3 -n 100`；`docker logs --tail 100 dududa-web-1` 中 Host 请求是否报错 |
| Web 日志显示 OneBot 未连接 | SnowLuma 容器、QQ 登录及注入状态；`networks.wsClients` 是否连接 `ws://dududa-web-api:8000/onebot/v11/ws`，且 token 与 `secrets/web/onebot_access_token` 一致 |
| 修改 SnowLuma 网络配置不生效 | WebUI `http://127.0.0.1:5099` 检查对应账号的连接；账号配置位于 `stacks/snowluma/data/gateway/config/onebot_<QQ号>.json`，不能只改全局模板。不要为检查配置反复重启 QQ |
| 指令有回应但提问失败 | run 的 `error`；`omp --version` 和 omp 登录状态；`journalctl` 中 `OmpError` / `OmpTimeout` |
| `This state directory is in use` | 已有 Host 占用该 `state_dir`；使用运行中 Host 的 API，或另设 `DUDUDA_V3_STATE_DIR` |
| `omp_available: false` | 单元的 `PATH` 或 `omp_binary` 配置 |
| 群里某些消息被忽略 | 是否在 `allowed_scopes`；是否点名（@ 或 `嘟嘟哒` 前缀）；未知 `/xxx` 指令会被忽略；对应任务是否被关闭（`task list`）；是否触发频率限制（run `reason=rate_limited`） |
| 主动推送没有发出 | outbox 条目状态：`pending` 表示 QQ 桥未在轮询（看 Web 日志），`unknown` 表示发送结果不确定且不会重试 |
| 校园查询不可用 | `docker ps` 中 `dududa-mcp-console-1` 是否运行，`curl http://127.0.0.1:8090`，能力是否列入 `campus_capabilities` |
| 课程资料显示无法读取 | 宿主未安装 `catdoc` / `libreoffice`，旧版 `.ppt` / `.doc` 课件会被标记为不可读 |
| 小红书归档失败 | 笔记需要登录时配置 `features.xiaohongshu.cookie` |
| 通知未推送 | `features.notify.enabled`、对应 `*_enabled`、任务开关；worker-venv 是否存在；`journalctl` 中 `notify` 相关警告 |
