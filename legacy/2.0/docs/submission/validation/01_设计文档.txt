摘要
校园群聊同时承载课程咨询、活动协调、通知转发与日常交流。面对多人交错发言、短句省
略、临时更正及分散的数据源，智能体需要连续完成情境理解、参与决策、资料查询和回答组
织。嘟嘟哒以QQ 群为主要交互场景，将这些职责拆分为上下文与感知、Social Engine、模型路
由、Capability/MCP、回答与Persona、输出适配等模块，并通过统一Python Runtime 编排。
系统经NapCat/OneBot v11 与AstrBot 接入QQ，使用Vue 3/Node.js 控制台管理群服务、模
型配置与运行记录。业务层已连接评课、第二课堂、教务、培养方案、校园通知与校车六类校园
服务。模型调用采用DeepSeek 的OpenAI 兼容Chat Completions 接口，模型档位、推理强度和可
见回答篇幅分别配置。管理员授权后，系统可以依据连续讨论和当前请求启用匹配的只读查询
插件。
本报告以自适应机制为技术主线：根据连续讨论与当前请求选择已授权插件；根据任务复
杂度、置信度和预算选择模型路由；根据群聊情境调整参与方式与表达；并以WebUI 工作台呈
现实际选择，支持按群配置、预览和调整。Memory v2 的作用域检索、中文BM25 和生命周期组
件，以及主动调度、离线Bandit 等研究成果一并说明，但不将其等同于已完成的长期群聊体验。
验证材料包含100 条固定消息的离线流程、真实MCP 原子查询、真实模型预览及模拟入站
记录。报告分别呈现测试输入、实际执行范围、结果与限制，保留早期广覆盖预览中发现的部分
通过和失败项，为评审者提供可核查的完成度说明。
关键词：群聊智能体；校园服务；语义感知；模型路由；MCP；可观察运行时
阅读说明。第1—4 节介绍目标、场景与架构；第5—9 节解释技术机制；第10节独立介绍WebUI
设计；第11—12节说明部署与验证；第13节及附录汇总本地资料和演进边界。文中方括号S 编号
对应附录的本地来源索引。

1 作品目标与设计思路
1.1 作品定位
嘟嘟哒是面向持续群体交流的社交智能体。其产品定位为“生活在QQ 群里的AI 群友”，技
术目标是在同一条运行链中完成理解群聊情境、判断参与方式、使用外部能力、形成回答并可靠
投递。校园生活与教学支持是首批应用场景，系统的接口划分同时支持向其他群体服务扩展。
群聊具有与单人问答不同的条件：当前消息可能只是一句追问，指向另一人的发言；同一时
间可能出现多个话题；群成员之间的更正具有先后关系；一次有用的回答也可能在错误的时机
造成打扰。因此，作品把“是否回应、回应谁、需要什么资料、如何表达”分别建模，使技术实
现能够围绕真实交互问题调整。
1.2 需要解决的问题
1. 信息分散。课程评论、活动、教务安排和通知分布于不同系统，用户需要反复切换页面，并
自行核对课程身份、时间范围和资料版本。
2. 上下文不完整。省略、引用、别称和更正使当前短句难以独立理解；仅拼接历史又可能把旧
安排当成现行事实。
3. 参与缺乏节奏。逐条回复会干扰讨论，单纯等待指令则难以利用连续讨论中已经形成的需
求。
4. 难以解释运行过程。模型、查询服务、配置和消息平台分别出错时，管理员需要知道具体失
败环节，以及保存的配置是否实际生效。
1.3 设计原则与工程选择
明确分工。输入适配器确认平台事件，感知模块解释语义，社交策略选择行动，能力层获取
资料，回答层组织内容。身份、群范围、执行权限和输出目标由程序维护，模型承担语义提取与
文本生成。
以业务能力连接异构服务。对智能体暴露的是课程查询、活动搜索、通知读取等业务单元。
具体MCP 工具名、参数投影和服务会话留在适配层。这样既能复用校验与错误处理，也便于保
留各数据源的差异。
按任务分配计算。模型档位、推理强度与输出篇幅独立配置，避免将“详细回答”直接解释
为“必须换更大的模型”。感知与回答分别选择模型角色和预算。
让运行可观察。QQ 与Web 预览共用Runtime；控制台展示实际运行模型、能力、耗时及结
果。开发验证使用同一套编排和可替换适配器，减少独立演示实现带来的偏差。
1.4 本次报告的实现口径
报告以2026 年9 月6 日本地主仓为对象。开始核对时主仓提交为2b52593，工作区还包含录
制与查询相关的在途改动；后续章节同时引用明确日期的已存验证材料。提交号用于定位源码，
不表示所有历史测试都运行于该提交，也不表示本次重新发布了程序。

2 应用场景与需求分析
2.1 用户与使用方式
主要使用者包括课程学习群中的学生、活动组织者、讨论组成员，以及维护智能体的群管理
员。群成员通过自然语言提问；明确提及Bot 时进入直接请求流程，开启自动参与后，连续群聊
也可以构成参与机会。管理员负责授予群服务权限、配置参与节奏，并在控制台检查运行情况。

2.2 功能需求
一次校园查询应能从自然语言定位业务服务，绑定必要参数，读取有来源的资料并形成可
理解的回答。信息不足时需要澄清；远端服务失败时应显示失败原因或可用的降级说明，不能把
未取得的资料补写为事实。
一次群聊参与应保留发言者、引用关系和当前问题，受到本群配置约束。自动启用只读插件
需要已有管理员授权，不能因发现一个新话题就安装任意代码或扩大服务范围。

4 功能模块与业务能力
4.1 六类校园服务
当前运行组合将五类MCP 校园服务与校车本地Provider 接入统一能力层。这里的“六类”
按面向用户的业务领域统计，不等于MCP 工具数量，也不包括控制台中仅登记的可选服务。
4.1.1 评课社区
评课能力支持课程与教师搜索、课程详情、评论、排名及统计。高层查询入口icourse.
public-query.v2 将业务操作与查询条件映射至iCourse 服务。回答需要区分同名课程、不同教师、
评论条数与站点统计；评论中的主观体验应表述为评论观点，不能转化为对课程或教师的确定
性评价。
在选课场景中，多位群友可以分别提出讲解细致程度、证明训练和作业负担等偏好。工具提
供课程与评论材料，回答模型负责按这些维度组织建议。若评论没有覆盖某一维度，应说明材料
不足；学期是否实际开课属于教务信息，不能仅靠评课社区推断。
4.1.2 第二课堂
二课服务提供活动搜索、详情、类别字典及连接状态。参数绑定处理活动关键词、类别、时
间和数量，返回活动名称、时间、报名状态与资料范围。运行环境通过部署端CAS 凭据访问服
务；群聊问答面向活动信息，个人学时、已报名记录、签到及代报名不属于本次智能体查询范围。
自然语言中“最近”“公开发布”“学术活动”等条件需要分别落实为查询或结果过滤。修复
记录表明，类别未绑定、活动详情参数错误或返回院系树过大，都会导致错误内容或过高的上下
文消耗。项目针对这些具体问题收敛了参数和返回结构。
4.1.3 教务公开信息
教务服务支持学期列表、全校开课、考试和教学日历。课程名称与教师来自开课记录，学期
和日期字段随结果保留。检索失败、空结果与没有考试安排是不同情况，回答应按实际返回区
分。当前接口不提供学生个人成绩查询，也不替代校方教务操作。
4.1.4 培养方案研究资料
培养方案服务按年级、专业、课程代码和方案类型查询，并支持方案与课程比较。数据来自
公开资料整理的非官方研究快照，当前来源覆盖2015—2026 级，快照日期为2026 年8 月2 日。
课程身份使用精确课程代码，防止同名课程在不同方案中被误合并。
该服务适合查阅和讨论培养要求。报告中的学分结果必须绑定年级、专业与方案类型；不能
把快照当成实时教务数据库，或把一次查询当成个人毕业资格审核。

4.1.5 校园通知

5 上下文感知与群聊参与机制
5.1 上下文范围与消息解释
消息适配保留消息标识、平台、机器人、会话、群、发言者、时间、提及与引用关系。Web
预览从服务端获取同账号、同群的近期历史；主动参与执行器读取当前群窗口。Runtime 继续按
预算整理这些资料，区分本轮问题、被引用内容和历史发言。
本轮指令决定要完成的任务，历史发言解释指代和讨论背景。例如，旧消息提出周五开会，
后续更正为周六，本轮追问“最终时间”，应依据有效更正形成答案。来源于其他群的引用文本
可以作为本轮提供的资料，但不能成为读取其他群完整历史的授权。
5.2 规则感知与模型感知合并
规则适合识别明确提及、已知业务词和输入格式；模型适合处理课程别称、口语、省略与开
放式需求。HybridPerceptionEngine 将两者组织为结构化感知结果，模型输出经过本地Schema 校
验后才能参与决策。当前感知并非向后续层直接透传任意自然语言推断。
结构化结果用于表达意图、实体、引用、偏好能力类别及置信信息。明确的“评课社区”提
示来源，课程实体提示查询对象；“最多三项”属于结果数量约束。模型只提供语义候选，最终
可用能力、执行预算和群权限仍由程序检查。
复杂度评估与社交决策分别使用感知信号。当前组合采用确定性策略，不为每一个阶段额
外调用一个大模型。高复杂度档位选择需要相应信号和置信条件，低置信、指代不明或任务缺项
可以进入澄清流程。

5.3 Social Engine 的动作选择
Social Engine 将对内容的理解转化为参与动作。当前核心策略包括直接回应、调用业务能
力、澄清和保持静默等行为路径；输入权限、群模式与当前请求条件影响选择。它与外围自动参
与执行器职责不同：前者决定本轮怎么处理，后者先判断普通群消息是否值得启动这一轮。
显式提及和自动参与使用不同入口。用户明确提出任务时，系统进入请求处理；自动参与则
在目标群已开启的前提下检查事件类型、概率、冷却、每小时上限及是否有进行中的运行。随机
抽样只影响参与机会，不应改变事实或服务权限。

以固定档位。当前路由没有调用在线Bandit 学习器。
这里的自适应体现为同一套策略针对不同任务作出不同选择。当前档位策略使用复杂度信
号及置信度：深度推理、独立核验、多约束综合等信号可支持选择较高档位；信号不足时使用默
认或较低档位，并检查预算和候选可用性。模型档位与选择原因进入运行结果，便于管理员理解
一次请求为什么采用相应计算配置。
推理额度与正文额度分别约束。如果回答只需一句话，模型仍可能需要充分推理；若用户需
要详细步骤，也不必仅因篇幅较长就提升任务复杂度。当前适配器将内部light/deep/maximum 映
射到DeepSeek 的low/high/max。无额外推理时发送thinking:disabled。
一次典型工具问答的等待时间可分解为
T = Tcontext + Tperception + Ttool + Tanswer + Toutput.
这只是运行阶段的拆分，不是测得的耗时模型。现有样本记录了总耗时，尚不足以量化各阶段的
平均贡献；后续优化应先区分工具等待与模型生成，再决定缓存或调用合并措施。

9.2 重复消息与输出确认
平台可能重推消息，用户也可能重试相同请求。核心依照消息与会话身份识别重复执行；输
出由独立的DeliveryRequest 和Receipt 描述，避免把准备好文本当作已经发送。接口测试覆盖并
发重复消息只运行一条模型和工具链，以及重复输出请求复用回执的行为。
实际网络中，超时可能发生在平台已收到消息但本地尚未取得确认之后。系统必须保留失
败与结果未知的区别。当前测试与记录可证明特定路径的去重和回执处理，不能据此承诺所有
故障下的端到端“恰好一次”投递。
9.3 会话范围与外部访问
会话范围贯穿上下文、群配置、能力执行和输出目标。浏览器不能任意指定一个群就读取其
完整资料；模型不能用生成文本扩大数据范围。二课凭据只在相应服务进程解析，报告示例使用
占位符；开放式文本与工具结果被视为资料，不成为更高权限指令。
当前安全机制包括确定性授权、参数与输出结构验证、受限工具目录、凭据外置和管理入口
认证。它们限制程序可以执行的动作，但不构成对所有提示注入、模型幻觉或错误判断的绝对保
证。评测应分别检查权限行为、数据处理和回答内容。

10.4 Agent 对话、运行与配置
Agent 面板将使用过程拆成三个页签：对话接收管理员请求并呈现回答与资料；运行展示实
际模型、推理与篇幅配置、使用的能力、耗时、上下文覆盖和错误原因；配置维护本群的行为偏
好、插件开关与参与策略。一次请求的运行信息与回答保持关联，管理员可以从结果直接追查执
行过程。
在当前正式Runtime 预览路径中，请求依次经过以下步骤：
1. 浏览器提交当前accountId、conversationId 和问题。
2. 网关校验输入与会话范围，从服务端读取同群近期历史；读取失败时直接说明原因。
3. 网关使用服务端凭据调用AstrBot 的Runtime 预览接口，由既有核心完成感知、路由、必要
查询和回答组织。
4. Runtime 返回回答、模型、能力、耗时和上下文用量，网关校验后交给页面呈现。
5. 管理员在“运行”页查看此次实际执行情况，再决定是否调整配置或继续提问。
预览模式可执行校园工具查询，但结果留在Web 中，返回的QQ 输出调用与长期记忆写入
均为0。QQ 手动消息发送属于聊天窗的独立操作。人工内测页则面向已配置样本和人工评价，
其结果与正式Runtime 预览分别记录。
配置以账号和会话为作用域，模型档位、推理强度、回答长度、回复强度、上下文预算和群
聊风格分别设置。页面区分管理员偏好、允许范围与锁定状态，并展示本轮有效选择；“上下文
长度”指历史读取预算，不能解释成模型服务商的最大上下文窗口。最终使用值以Runtime 返回
结果为准。
10.5 模型、工具与服务管理
模型管理按Luna、Terra、Sol 三个档位组织连接和Key 池，显示真实模型ID、接入地址、推
理参数、超时、输出额度及Key 可用状态。相同底层模型可以服务不同档位，选项使用档位标识
区分，避免按模型名称合并后选择错位。
配置编辑、保存和运行生效有各自的反馈。模型连接保存后，页面读取Runtime 配置状态；
管理员执行“应用到Runtime”后，等待服务端确认，再用一次请求观察实际模型。这样可以定
位“内容已保存，但运行侧仍使用旧配置”的问题。

13 创新点、资料整合与演进路线
13.1 作品的创新点
嘟嘟哒的核心设计主线是自适应：以当前讨论与任务为输入，在管理员设定的范围内选择参
与方式、业务插件和计算路由，并通过WebUI 呈现实际结果。自适应分别落实到能力选择、计
算选择和交互选择，形成可解释的群聊服务机制。

自适应插件选择。系统综合讨论主题、多人参与、需求持续性与当前请求，在管理员预先授
权的只读服务中选择并启用匹配插件。以选课讨论为例，群成员逐步提出讲解方式、证明训练和
课业负担等条件，当前请求达到触发条件后，系统启用评课插件并进入课程资料查询。能力选择
因此与连续讨论关联，减少用户记忆命令和手动切换服务的负担；启用原因与实际能力调用可
在运行记录中核对。实现机制见第5.4、7 节。
任务驱动的自适应路由。感知结果提供意图与复杂度信号，档位策略结合置信度、可用模型
和预算选择本轮计算配置，路由器再校验角色、能力与输出容量。简单交流、校园查询和复杂比
较可以使用不同档位；推理强度与可见篇幅分别控制，避免仅按答案长短分配计算资源。自适应
体现在运行选择随任务改变，选择依据可记录并在WebUI 中查看。当前策略由规则和配置定义，
其工程目标是匹配任务所需的计算投入；尚未完成同条件成本与效果对照实验。机制见第6 节。
自适应群聊参与与表达。系统根据提及、追问、持续讨论和群策略决定回复、查询、澄清或
静默，再结合任务要求组织回答篇幅与人格表达。参与选择与冷却、频率限制分别执行，既利用
多人交流中的情境信号，也保持管理员对参与节奏的控制。工具事实与Persona 分层，使严谨解
释和日常表达能够在同一运行路径中按需组织。机制见第5、8 节。
WebUI 工作台设计。工作台将真实QQ 会话与Agent 对话、运行、配置置于统一界面，并在
桌面并排布局与手机单页切换中保留当前账号和会话。管理员按群设置偏好、允许范围与锁定
项，运行后查看实际模型、插件、上下文覆盖、耗时和选择原因，再调整策略。QQ 与Web 预览
共享核心，构成“配置—预览—观察—调整”的连续操作，使自适应机制既能被配置，也能被检
查。详细设计见第10节。
这些创新属于校园群聊场景下的系统设计与交互机制创新。当前自适应由语义感知、确定
性规则、管理员配置与运行状态共同实现；在线Bandit、长期记忆学习和策略更新另有独立研究
与接入计划。

13.3 资料中的主要差异及处理
旧状态与新实现。文档站的架构页面固定在早期提交，current-state.md 也包含重构前基线；
其中“尚未实现”或旧插件清单不能覆盖当前组合根。新版按现有源码描述运行路径，历史状态
用于解释演进。
原型与主仓。历史dududa20-prototype 和dududa20-plugin 记录过多步规划、八角色路由、个
人信息及记忆等功能，并有自己的测试数字。当前主仓采用不同的实现、组合和阶段划分，新报
告不把它们视为同一发布物。
设计目标与组件接入。完整Memory、主动日报、多OC 和Skill 组合在多份资料中反复出现。
源码存在、离线验证、配置登记、正式接入与长期效果是不同证据，当前状态已在第12节统一。
模型配置与测试口径。Luna/Terra/Sol 是档位别名，旧材料中还使用过其他模型；本次演示
记录使用DeepSeek。常规推理强度与录制时关闭thinking 的配置分别注明，不把测试数量或样
本时延外推到全部模型。
13.4 下一阶段的技术路线
近期优先改进来源覆盖、查询前澄清、近期摘要的时间与归属，分解等待时间，并对现有广
覆盖题集完成同范围的真实模型复测。参与机制需要在获准的自然群窗口上评估时机、回应对
象、误触发和重复建议，而不只评估是否成功生成文字。
随后接入Memory 的显式写入、检索、删除与反馈闭环，在真实但经授权的数据上比较无记
忆、近期优先和BM25。多OC 与群友印象应在有明确资料来源和修改方式的基础上建设。
较长远的扩展是以现有业务能力为基础的多步Skill，以及同角色、同任务范围内的路由优
化。二者均应从具体任务和可测收益出发，保持当前业务的可维护性，并保留用户与管理员对群
聊参与的控制。
